# OpenHero68 service v0.6.1 / UI v0.9.59

Verifies the HERO84 key table against the official AULA web driver, so the
84-key board is checked without a physical unit.

The AULA driver's `AULA_2829` (HERO 84 HE) WIN key layer lists all 84 keys with
their protocol positions. That table is now extracted into
`tests/fixtures/hero84-official-layout.json` (regenerate with
`tools/extract-hero84-layout.mjs`) and `tests/hero84-official-layout.test.mjs`
asserts that:

- `HERO84_KEY_POSITIONS` matches the official `pos` of every key;
- the 68 HERO68 keys keep the same `pos` on HERO84;
- the 16 HERO84-only keys (F1-F12, `~`, PrtSc, Home, End) and the made-up
  `matrixKey` rows are the ones the official layout adds;
- the six rows match the official row sizes (16/15/15/14/14/10) and key order.

This confirms the earlier concern was unfounded: HERO68 and HERO84 share one key
table for the 68 common keys, and remap/switch batching already matches the
driver's chunk sizes (`sync_keys` 9 keys per batch, `sync_key_type` 18 records).

The F1-F12 keys in the HERO84 layout are now generated from one base value
instead of being listed individually; the resulting layout is unchanged.

`docs/hero84-verification.md` records what is proven and what still needs a real
board: firmware matrix cells for the new keys, read chunk sizes for
`fetch_key_type` / `safe_area`, Hall distance units, the firmware light palette,
and the HERO84 switch-ID table.

Not validated on a physical HERO84. The 212-byte CMD08 frame, the mirrored
colours for the extra keys and any HERO84-specific firmware behaviour still need
a real board.

Install the complete Windows setup to update the native app.

Validation: 616 JavaScript tests pass (6 new), the web and service TypeScript
builds pass, and the Cloudflare Pages deployment serves `/api/health`. Physical
HERO84 behaviour is unverified.
