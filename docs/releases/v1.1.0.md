# OpenAula v1.1.0

A structural release: the same features with each concern in one place, plus a
Gamepad toggle binding and a Cloudflare deploy that runs from GitHub Actions.

## Gamepad: bind Start/Stop to a key

The Gamepad page can now hold Start/Stop on a toggle key. The app tracks the
held key locally, so autorepeat cannot fire twice, and sends the state it
expects (`expectedEnabled`) with `POST /gamepad/toggle`; the service only
changes when that expectation matches, so a retried request cannot flip the
emulation back on or off behind your back.

Not validated on a physical board: the binding, the toggle round trip and the
`expectedEnabled` guard were exercised by the automated tests only.

## Structure

None of your settings change; the code moved.

- The Windows service splits into `service/server/` (HTTP routing),
  `service/rgb/`, `service/gamepad/`, `service/hall/` and `service/bridge/`
  instead of one large `service/main.ts`.
- The HERO68 protocol lives in `src/protocol/bytetech/`. The old
  `src/protocol/hero68/` paths still re-export, so nothing outside this
  repository breaks.
- The web app delegates selection, per-key performance, profile workspace,
  Hall view-model and sync state to `src/app/hooks/`, and its profile and
  settings screens to `src/pages/`.
- The boards registry is the only key table: `heroLayout()` caches one view per
  registered board and `keyIdsOf()` is the single place that drops row padding
  slots, so a layout edit no longer has to be repeated in two places.

## Fixes

- My Profile showed "68 keys" and "your HERO68" even for a connected HERO84; it
  now reads the key count and the model name from the board registry.
- `public/_headers` no longer starts with a byte-order mark, which Cloudflare
  rejected as `Invalid _headers configuration: Line 1: Expected a path before
  headers` when deploying the Worker.

## Cloudflare

`.github/workflows/cloudflare.yml` builds on every push to main and deploys the
Worker with `wrangler deploy` once `CLOUDFLARE_API_TOKEN` and
`CLOUDFLARE_ACCOUNT_ID` are set. Pull requests from forks skip the deploy so
they never see the token. The same workflow now typechecks the service, which
the web build alone did not cover.

## Windows setup

Version 1.1.0 covers the app and the service together, as 1.0.0 did. The
installer and the signed update manifest are built by the Windows setup
workflow; the upgrade path is checked by the installer smoke test, not against
a real 1.0.0 installation.

## Validation

627 JavaScript tests pass, the web build passes, and both the web and service
TypeScript projects typecheck. HERO84 remains unvalidated on a physical board.
