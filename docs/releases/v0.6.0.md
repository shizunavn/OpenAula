# OpenHero68 service v0.6.0 / UI v0.9.58

Adds AULA HERO84 HE support to the Windows service and the web app, and fixes
the emulated RGB preview for HERO84-only keys.

The service now remembers the connected model (HERO68/HERO84, detected from the
device UUID), logs the real model name and reports `deviceModel` in `/status`.
Custom RGB frames for a HERO84 also address its 16 extra keys (F1-F12, `~`,
PrtSc, Home, End). The engine still renders 68 keys, so each extra key copies
the colour of the HERO68 key in the same column/slot; HERO68 output is
unchanged. Native Rhythm gets the same mapping through a `device-model:<id>`
bridge command that older bridges ignore, and `/hall/stream` accepts all 84
HERO84 keys while still limiting a HERO68 to 68.

Web app fixes: the emulated firmware preview no longer crashes on keys outside
the 68-node LED map, per-key colour read errors name the offending position, and
model detection keeps the detailed USB product name.

The web app now asks the keyboard itself (`CMD 0x82` zone 1) for its device UUID
when it connects, through WebHID or the Windows service, and refuses a board that
does not report a HERO68/HERO84 UUID. A connected board therefore decides the
model: the model selector is disabled while connected, and profile reads stay
blocked (and saves disabled) until the model is verified, so a HERO68 is never
written with HERO84 key tables or the other way round.

Not validated on a physical HERO84. The 212-byte CMD08 frame, the mirrored
colours and the remap/RGB batching against the official driver still need a real
board. Per-key custom effects and Rhythm patterns have no HERO84 geometry yet,
so the extra keys mirror their source keys instead of animating independently.

Install the complete Windows setup to update the native app.

Validation: 610 JavaScript tests pass, the web and service TypeScript builds
pass, and the Cloudflare Pages deployment serves `/api/health`. Physical HERO84
behaviour is unverified.
