# OpenAula v1.3.0

WIN 68 HE MAX lighting and a Gamepad connection fix.

## WIN 68 HE MAX lighting

The board now has its own lighting path on the XSYD (`0x5C`) protocol instead
of going through the HERO68 `0x09` encoders:

- Global zone (`0x18`): effect, brightness, speed, animation direction, and a
  seven-slot palette. Frames match `connect_keyboard_to_webhidofficial.pcapng`
  and `profile_1_2_3_4.pcapng`.
- Per-key colour (`0x2A`): single-key writes (`LEN=5`) and the five-frame
  readback that returns 68 keys in batches of 14. Checked against
  `Q(green)-E(red) -Z(yellow)-P(Pink).pcapng`.
- Every frame is checksummed the way the firmware does it and is written to a
  more realistic USB write budget than before, so a slow board no longer
  drops the tail of a batch.

The Custom Effects editor and the live preview render the WIN 68 HE MAX
layout while editing.

## Gamepad on WIN 68 HE MAX

When OpenAulaService was already running, the Gamepad page picked the service
path and sent HERO68's `0x82` UUID request to a board that only speaks
`0x5C`. Nothing answered within the 800 ms native timeout, so the page showed
`timeout` while the same code worked on HERO68.

- WebHID is now preferred whenever the WIN 68 HE MAX is connected, whether or
  not the service is running.
- The handoff to the service stops when an XSYD board is connected to the
  browser, so the `0x82` request is never sent to it.
- Hall demand for the gamepad follows the native output state instead of a
  TypeScript mirror that is still `false` while a start is paused. The board
  is polled during startup instead of reporting a stale neutral.
- XSYD commands the service cannot serve now fail with
  `error:unsupported` instead of waiting for a reply that will never come.

## Validation

670 JavaScript tests pass, the web build passes, both TypeScript projects
typecheck, and the native Hall/gamepad checks pass. The XSYD frames are
verified by replaying the captures, not against a physical board from this
repository.
